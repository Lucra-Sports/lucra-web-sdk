# Games You Play Headless

Headless functions for Games You Play (recreational game) matchups; reads work before login, writes need a logged-in user. For the shared mechanics every call relies on (the invisible iframe, lifecycle gating, timeouts, and the full error table) see [Headless on Web](2.0_headless.md).

## Reading a matchup

`api.matchup(matchupId)` resolves with one recreational game matchup. It needs no login: it awaits iframe initialization internally (no `await client.ready` needed), so you can render a shared matchup before the user logs in. Calls run concurrently, each with its own [15-second timeout](2.0_headless.md#request-timeout).

```typescript
const matchup = await client.api.matchup(matchupId);
const stake =
  matchup.atStake.type === 'CASH'
    ? `$${matchup.atStake.amount}`
    : matchup.atStake.reward.title;
```

An unknown id, or the id of a matchup that is not a recreational game, rejects with a `LucraApiError` with code `API_ERROR` and message `"Recreational game matchup not found"`. Unlike other `API_ERROR` failures, retrying does not help.

Matchup payloads include other users' ids (`creatorId`, `participantGroups[].userIds`). Do not log them or send them to analytics.

### `LucraMatchup`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | The matchup id |
| `status` | `LucraMatchupStatus` | See below |
| `playStyle` | `LucraPlayStyle` | `"GROUP_VS_GROUP"` (teams) or `"FREE_FOR_ALL"` |
| `isPublic` | `boolean` | |
| `createdAt` | `string` (optional) | ISO timestamp |
| `creatorId` | `string` | User id of the creator |
| `winningGroupId` | `string` (optional) | Id of the winning participant group, once there is one |
| `game` | `LucraRecreationalGame` | The game being played |
| `atStake` | `LucraAtStake` | What the matchup is played for |
| `participantGroups` | `LucraMatchupParticipantGroup[]` | The matchup's groups (teams), ordered by creation |

`LucraMatchupStatus` is one of `OPEN`, `CONFIRMED`, `LOCKED`, `PENDING_OUTCOMES`, `ON_HOLD`, `DISPUTE`, `CLOSED`, `CLOSED_TIE`, `CANCELED_BY_OWNER`, `CANCELED_DISPUTE`, `CANCELED_GAME_CANCELED`, `CANCELED_NOT_ACCEPTED`, `CANCELED_PLAYER_INACTIVE`, `CANCELED_THROUGH_API`, or `CANCELED_TIMEOUT`. The `CLOSED*` values mean the matchup finished; the `CANCELED_*` values mean it was canceled.

### `LucraAtStake`

A union discriminated by `type`:

| `type` | Field | Notes |
| --- | --- | --- |
| `"CASH"` | `amount: number` | Cash buy-in per participant |
| `"TENANT_REWARD"` | `reward: LucraReward` | Your reward the matchup is played for: `{ rewardId, title, descriptor, iconUrl, bannerIconUrl, disclaimer, metadata }`. See [Rewards](1.9_rewards.md) |

### `LucraRecreationalGame`

| Field | Type | Notes |
| --- | --- | --- |
| `gameId` | `string` | Game type id, e.g. `"AIR-HOCKEY"` |
| `name` | `string` | Display name |
| `iconUrl` | `string` (optional) | |
| `minigameEnabled` | `boolean` | Whether the game type can be played as a Lucra minigame |

### `LucraMatchupParticipantGroup`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | Group (team) id |
| `userIds` | `string[]` | User ids of the group's participants; empty when nobody has joined it |

## Matchup details

`api.matchupDetails(matchupId)` resolves with the matchup plus who is in each group, each group's standing and score, and per-player scores. Like `api.matchup`, it needs no login, awaits iframe initialization internally, runs concurrently, and rejects an unknown or non-recreational id with `API_ERROR` and `"Recreational game matchup not found"`.

```typescript
const { matchup, groups, participantScores } = await client.api.matchupDetails(matchupId);
const winner = groups.find((g) => g.id === matchup.winningGroupId);
```

The participant fields (`userId`, `username`, `avatarUrl`) are other users' data. Do not log them or send them to analytics.

### `LucraMatchupDetails`

| Field | Type | Notes |
| --- | --- | --- |
| `matchup` | `LucraMatchup` | The same object `api.matchup` returns |
| `groups` | `LucraMatchupGroup[]` | Every group, including empty ones, in the same order as `matchup.participantGroups` |
| `participantScores` | `LucraMatchupParticipantScore[]` | Per-player scores ordered by `place`; may be empty |

### `LucraMatchupGroup`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | Group (team) id, matching `matchup.participantGroups[].id` |
| `outcome` | `"WIN" \| "LOSS" \| "TIE"` (optional) | The group's current standing: `WIN` is currently winning or has won, `LOSS` is currently losing. It is not only the final result; use `matchup.winningGroupId` for the final winner |
| `score` | `number` (optional) | The group score with any override applied |
| `participants` | `LucraMatchupParticipant[]` | Empty when nobody has joined the group |

### `LucraMatchupParticipant`

| Field | Type | Notes |
| --- | --- | --- |
| `userId` | `string` | |
| `username` | `string` | |
| `avatarUrl` | `string` (optional) | |
| `individualPayout` | `number` (optional) | What this user receives if their group wins, after the fee and team split. Absent for tenant rewards |

### `LucraMatchupParticipantScore`

| Field | Type | Notes |
| --- | --- | --- |
| `userId` | `string` (optional) | |
| `username` | `string` (optional) | |
| `avatarUrl` | `string` (optional) | |
| `place` | `number` (optional) | Rank, 1 is first |
| `score` | `number` (optional) | |
| `finishedAt` | `string` (optional) | ISO timestamp |
| `groupId` | `string` (optional) | The participant's group |

## Fee

`api.gamesMatchupFee()` resolves with the games (minigame) matchup service fee as a fraction: `0.05` is 5%. It is the same value the mobile SDKs expose as `observeGamesMatchupFee`, and `0` when the tenant has no fee configured. It is not the fee on recreational (Games You Play) cash matchups: the backend applies that per wager, and `LucraMatchupParticipant.individualPayout` in [matchup details](#matchup-details) already reflects it.

Like `api.matchup`, it needs no login, awaits iframe initialization internally, and runs concurrently. It rejects with a `LucraApiError` with code `API_ERROR` when Lucra cannot read the configuration.

```typescript
const fee = await client.api.gamesMatchupFee();
const percent = fee * 100; // 5
```

## Live details

`api.subscribeToMatchupDetails(matchupId)` resolves with the current `LucraMatchupDetails`, like [`api.matchupDetails`](#matchup-details), then keeps it live: each change to the matchup (a player joins, a score or status changes) arrives as a `matchupDetailsUpdated` event carrying the full, fresh `LucraMatchupDetails`. The first update may repeat the snapshot. Like `api.matchup`, it needs no login, awaits iframe initialization internally, and rejects an unknown or non-recreational id with `API_ERROR` and `"Recreational game matchup not found"`.

There is one subscription at a time: subscribing again replaces it, and only the latest matchup's updates reach listeners. `api.cancelMatchupDetailsSubscription()` stops the updates and the Lucra app's live connection. It never throws, so it is safe in cleanup before `open()` or after `close()`; `close()` also ends the subscription. If the iframe reloads, the SDK subscribes again on its own to an active subscription. A subscribe still in flight when the iframe reloads is not resent: it rejects with `"Timeout"`, so subscribe again.

A pending subscribe that a newer subscribe or a cancel replaces rejects with a string starting with `"Cancelled by"`. It is benign: do not surface it to users.

```typescript
import type { LucraMatchupDetails } from 'lucra-web-sdk';

const onUpdate = (details: LucraMatchupDetails) => render(details);
client.on('matchupDetailsUpdated', onUpdate);

client.api
  .subscribeToMatchupDetails(matchupId)
  .then(render)
  .catch((e) => {
    if (typeof e === 'string' && e.startsWith('Cancelled by')) return;
    showError(e);
  });

// Cleanup, e.g. when the view unmounts:
client.off('matchupDetailsUpdated', onUpdate);
client.api.cancelMatchupDetailsSubscription();
```

Updates carry the same participant data as [matchup details](#matchup-details): do not log them or send them to analytics.

## Creating a game

`api.createRecreationalGame(input)` creates a matchup for the logged-in user and resolves with `{ matchupId, matchup }`. Unlike the reads it needs a login and does not wait for initialization: call it after `await client.ready`, like [`api.joinTournament`](2.0_headless.md#api-functions). The Lucra app validates the input, runs the buy-in checks, and creates the matchup; there is no Lucra UI in between.

```typescript
import { LucraApiError } from 'lucra-web-sdk';

await client.ready;
try {
  const { matchupId, matchup } = await client.api.createRecreationalGame({
    gameTypeId: 'AIR-HOCKEY',
    atStake: { type: 'CASH', amount: 5 },
    playStyle: 'GROUP_VS_GROUP',
  });
} catch (e) {
  if (e instanceof LucraApiError) {
    // Branch on e.code, see Errors below
  }
}
```

### `LucraCreateRecreationalGameInput`

| Field | Type | Notes |
| --- | --- | --- |
| `gameTypeId` | `string` | Game type id, e.g. `"AIR-HOCKEY"` (`LucraRecreationalGame.gameId`) |
| `atStake` | `LucraAtStake` | `{ type: "CASH", amount }` or `{ type: "TENANT_REWARD", reward }`, see [`LucraAtStake`](#lucraatstake) |
| `playStyle` | `LucraPlayStyle` | `"GROUP_VS_GROUP"` or `"FREE_FOR_ALL"` |

The geo compliance context comes from the game's own configuration, not from the input. For `TENANT_REWARD`, `reward` is a `LucraReward` that needs a non-empty `rewardId`. It should be one of the rewards your server offers (for example the list you send with [`sendMessage.availableRewards`](1.9_rewards.md)): the host supplies it, so verify `rewardId` on your server when handling the [`claimReward`](1.6_lucra_event_listener.md) event.

### Result

`LucraRecreationalGameResult` is `{ matchupId: string, matchup: LucraMatchup | null }`. After a successful create the Lucra app reads the matchup back. If that read fails, `matchup` is `null` but the matchup **was created**: do not retry, or the user gets a second one. Fetch it with [`api.matchup(matchupId)`](#reading-a-matchup) instead.

### Errors

The call rejects with a [`LucraApiError`](2.0_headless.md#lucraapierror-by-code). The checks run in a fixed order: the account check (blocked or suspended), then input validation (before any network call), then the buy-in checks: funds, then identity or demographics, then location.

| `code` | Cause | Remediation |
| --- | --- | --- |
| `INVALID_AT_STAKE`, `INVALID_REWARD_TYPE`, `INVALID_PLAY_STYLE` | Invalid input; `message` names the field. A cash `amount` must be within the tenant's allowed range | Fix the input; do not retry as is |
| `NOT_ALLOWED` | The account is blocked or suspended, checked before input validation. Also raised by the SDK, with nothing posted, when another create is still pending: `"Another createRecreationalGame request is already in progress"` | Show `message`; do not retry |
| `INSUFFICIENT_FUNDS` | The balance does not cover the buy-in | `client.popup().deposit()`, then retry |
| `UNVERIFIED` | Identity verification is incomplete | `client.dialog().kyc()`, then retry |
| `DEMOGRAPHIC_INFORMATION_MISSING` | Profile information is missing | `client.dialog().demographic()`, then retry |
| `LOCATION_NEEDED` | No location for the user yet | `client.dialog().locationGrant()`, then retry |
| `LOCATION_ERROR` | The location check failed | Show `message` as is |
| `API_ERROR` | `"Game not found"` (unknown `gameTypeId`) or `"gameTypeId is required"`: a definite error, nothing was attempted. Any other failure: the outcome is unknown, see below | Show `message` |

The remediation steps are the same as for joining a tournament, see the [error table](2.0_headless.md#lucraapierror-by-code). Every code above `API_ERROR`, and the two `API_ERROR` messages above, are raised before anything is created.

**`"Timeout"`, any other `API_ERROR`, and a `LucraClientNotOpen` rejection because the client was closed while the create was pending, all mean the outcome is unknown**: the matchup may have been created even though the call rejected. Never retry automatically. Check the user's matchups first, and create again only if the matchup is missing.

### Timeout and pending calls

A create has a 60-second timeout instead of 15, because it can wait on the location check. It is not single-flight: while one create is pending, a second call rejects at once with `NOT_ALLOWED` (`"Another createRecreationalGame request is already in progress"`) and posts nothing, and the first call settles normally. Still disable your create button while a call is pending, so users never see that rejection.

## Accepting a versus game

`api.acceptVersusRecreationalGame(matchupId, teamId)` joins the logged-in user to one team of a `GROUP_VS_GROUP` matchup and resolves with `{ matchupId, matchup }`, the same [`LucraRecreationalGameResult`](#result) as a create. Like a create it needs a login and does not wait for initialization: call it after `await client.ready`. The Lucra app checks the matchup, runs the buy-in checks, and joins the user; there is no Lucra UI in between.

`teamId` is the id of one of the matchup's groups: `matchup.participantGroups[].id` from [`api.matchup`](#reading-a-matchup), or `details.groups[].id` from [`api.matchupDetails`](#matchup-details) (empty groups are included there). Read the matchup first and let the user pick a team.

```typescript
await client.ready;
const matchup = await client.api.matchup(matchupId);
const teamId = matchup.participantGroups[0].id;
try {
  const result = await client.api.acceptVersusRecreationalGame(matchupId, teamId);
} catch (e) {
  if (e instanceof LucraApiError) {
    // Branch on e.code, see Errors below
  }
}
```

If `matchup` in the result is `null`, the user **did join**: the read after the accept failed. Do not retry; fetch it with [`api.matchup(matchupId)`](#reading-a-matchup).

### Errors

The call rejects with a [`LucraApiError`](2.0_headless.md#lucraapierror-by-code). The checks run in a fixed order: the account check (blocked or suspended), then the matchup checks, then the buy-in checks: funds, then identity or demographics, then location.

| `code` | Cause | Remediation |
| --- | --- | --- |
| `NOT_ALLOWED` | The matchup is not `OPEN`; it is not a `GROUP_VS_GROUP` matchup (a free-for-all matchup is joined with `api.acceptFreeForAllRecreationalGame`); `teamId` is not a group of the matchup; the user is already in the matchup, which includes the creator trying to accept their own matchup; or the account is blocked or suspended. `message` says which. Also raised by the SDK, with nothing posted, when another accept is still pending: `"Another acceptRecreationalGame request is already in progress"` | Show `message`; do not retry |
| `INSUFFICIENT_FUNDS` | The balance does not cover the buy-in | `client.popup().deposit()`, then retry |
| `UNVERIFIED` | Identity verification is incomplete | `client.dialog().kyc()`, then retry |
| `DEMOGRAPHIC_INFORMATION_MISSING` | Profile information is missing | `client.dialog().demographic()`, then retry |
| `LOCATION_NEEDED` | No location for the user yet | `client.dialog().locationGrant()`, then retry |
| `LOCATION_ERROR` | The location check failed | Show `message` as is |
| `API_ERROR` | `"Recreational game matchup not found"` (unknown id, or not a recreational game): a definite error, nothing was attempted. Any other failure: the outcome is unknown, see below | Show `message` |

The remediation steps are the same as for [creating a game](#errors) and joining a tournament, see the [error table](2.0_headless.md#lucraapierror-by-code). Every code above `API_ERROR`, and the `"Recreational game matchup not found"` message, are raised before the user joins.

**`"Timeout"`, any other `API_ERROR`, and a `LucraClientNotOpen` rejection because the client was closed while the accept was pending, all mean the outcome is unknown**: the user may have joined even though the call rejected. Never retry automatically. Read the matchup with `api.matchup(matchupId)` first and accept again only if the user is not in a group.

### Timeout and pending calls

An accept has a 60-second timeout instead of 15, because it can wait on the location check. It is not single-flight: while one accept is pending, a second call rejects at once with `NOT_ALLOWED` and posts nothing, and the first call settles normally. The free-for-all accept shares this one in-flight slot, so a free-for-all accept and a versus accept cannot be pending at the same time. Disable your join buttons while a call is pending, so users never see that rejection.

## Accepting a free-for-all game

`api.acceptFreeForAllRecreationalGame(matchupId)` joins the logged-in user to a `FREE_FOR_ALL` matchup and resolves with `{ matchupId, matchup }`, like [`api.acceptVersusRecreationalGame`](#accepting-a-versus-game). There is no team to pick: a free-for-all matchup has no teams to choose between, so the call takes only the matchup id. Call it after `await client.ready`.

```typescript
await client.ready;
try {
  const result = await client.api.acceptFreeForAllRecreationalGame(matchupId);
} catch (e) {
  if (e instanceof LucraApiError) {
    // Branch on e.code, see Errors above
  }
}
```

The [errors](#errors-1), the unknown-outcome cases, the `null` `matchup` rule, and the 60-second timeout are the same as for a versus accept. One difference: calling it on a `GROUP_VS_GROUP` matchup rejects with `NOT_ALLOWED` and nothing happens. Check `matchup.playStyle` and call the function that matches. It shares the versus accept's in-flight slot: while either accept is pending, the other rejects at once with `NOT_ALLOWED` (`"Another acceptRecreationalGame request is already in progress"`) and posts nothing.
