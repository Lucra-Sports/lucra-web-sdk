# Games You Play Headless

Render Games You Play (GYP, recreational game) matchups in your own UI, keep them live, and create, accept, and cancel them from your own buttons, with no Lucra screen in between. Gameplay itself still runs in Lucra UI: hand off with `client.dialog().matchupDetails(matchupId)` (see [Lucra Flows](1.3_lucraflows.md#dialogs)). Login, KYC, demographics, deposits, and the location grant stay Lucra flows too; the [errors](#errors-and-remediation) tell you when to present them.

For the shared mechanics (the invisible iframe, lifecycle gating, `LucraClientNotOpen`, the full error table) see [Headless on Web](2.0_headless.md).

## Auth model

- **Reads work before login.** `matchup`, `matchupDetails`, and `subscribeToMatchupDetails` await iframe initialization internally, so call them without `await client.ready`, for example to show a shared matchup to a logged-out visitor.
- **Writes need a logged-in user.** `createRecreationalGame`, `acceptVersusRecreationalGame`, `acceptFreeForAllRecreationalGame`, and `cancelRecreationalGame` send at once without waiting for initialization: call them after `await client.ready`. The Lucra app never answers a write from a logged-out session, so it rejects with `"Timeout"` after 60 seconds.
- **Matchup data identifies other users.** `creatorId`, `participantGroups[].userIds`, and each participant's `userId`, `username`, and `avatarUrl` are other users' data. Do not log them or send them to analytics.

## Functions

| Function | Auth | Timeout | Concurrency |
| --- | --- | --- | --- |
| `api.matchup(matchupId)` | None | 15s | Concurrent: each call settles with its own response |
| `api.matchupDetails(matchupId)` | None | 15s | Concurrent |
| `api.subscribeToMatchupDetails(matchupId)` | None | 15s for the snapshot | One subscription: a new call replaces the previous one |
| `api.cancelMatchupDetailsSubscription()` | None | None (returns `void`) | Never throws |
| `api.createRecreationalGame(input)` | Logged in | 60s | One at a time |
| `api.acceptVersusRecreationalGame(matchupId, teamId)` | Logged in | 60s | One accept at a time, shared with the free-for-all accept |
| `api.acceptFreeForAllRecreationalGame(matchupId)` | Logged in | 60s | Shares the versus accept's slot |
| `api.cancelRecreationalGame(matchupId)` | Logged in | 60s | One at a time |

- Signatures and return types are in the [API functions table](2.0_headless.md#api-functions).
- Every call except `cancelMatchupDetailsSubscription` rejects with [`LucraClientNotOpen`](2.0_headless.md#lucraclientnotopen) before `open()` or after `close()`, and `close()` rejects the ones still pending with it.
- Writes get 60 seconds because they can wait on the location check.
- "One at a time": while a write is pending, a second call of the same kind rejects at once with `NOT_ALLOWED` (`"Another createRecreationalGame request is already in progress"`, or `acceptRecreationalGame` / `cancelRecreationalGame`), posts nothing, and leaves the first to settle normally. Disable the button while its call is pending so users never see this.
- Writes run on a blank route in the hidden iframe and leave it there. To show Lucra UI afterwards, open it with `dialog()` or `redirect()`, not `show()` alone.

## Reading a matchup

`api.matchup(matchupId)` resolves with one `LucraMatchup`.

```typescript
const matchup = await client.api.matchup(matchupId);
const stake =
  matchup.atStake.type === 'CASH'
    ? `$${matchup.atStake.amount}`
    : matchup.atStake.reward.title;
```

Every function that takes a `matchupId` rejects an unknown id, or the id of a matchup that is not a recreational game, with `API_ERROR` and the message `"Recreational game matchup not found"`. Unlike other `API_ERROR` failures, retrying does not help.

### `LucraMatchup`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | The matchup id |
| `status` | `LucraMatchupStatus` | See below |
| `playStyle` | `LucraPlayStyle` | `"GROUP_VS_GROUP"` (teams) or `"FREE_FOR_ALL"` |
| `isPublic` | `boolean` | |
| `createdAt` | `string` (optional) | ISO timestamp |
| `creatorId` | `string` | User id of the creator |
| `winningGroupId` | `string` (optional) | Id of the winning participant group, once there is one |
| `game` | `LucraRecreationalGame` | The game being played |
| `atStake` | `LucraAtStake` | What the matchup is played for |
| `participantGroups` | `LucraMatchupParticipantGroup[]` | The matchup's groups (teams): the creator's group first, then the rest in creation order |

`LucraMatchupStatus` is one of `OPEN`, `CONFIRMED`, `LOCKED`, `PENDING_OUTCOMES`, `ON_HOLD`, `DISPUTE`, `CLOSED`, `CLOSED_TIE`, `CANCELED_BY_OWNER`, `CANCELED_DISPUTE`, `CANCELED_GAME_CANCELED`, `CANCELED_NOT_ACCEPTED`, `CANCELED_PLAYER_INACTIVE`, `CANCELED_THROUGH_API`, or `CANCELED_TIMEOUT`. The `CLOSED*` values mean the matchup finished; the `CANCELED_*` values mean it was canceled. Only `OPEN` matchups can be accepted or canceled.

### `LucraAtStake`

What a matchup you read is played for, a union discriminated by `type`. Matchups created in Lucra's own UI can have a `TENANT_REWARD` stake; headless create is cash only ([`LucraCashStake`](#lucracreaterecreationalgameinput)).

| `type` | Field | Notes |
| --- | --- | --- |
| `"CASH"` | `amount: number` | Cash buy-in per participant |
| `"TENANT_REWARD"` | `reward: LucraReward` | Your reward the matchup is played for: `{ rewardId, title, descriptor, iconUrl, bannerIconUrl, disclaimer, metadata }`. See [Rewards](1.9_rewards.md) |

### `LucraRecreationalGame`

| Field | Type | Notes |
| --- | --- | --- |
| `gameId` | `string` | Game type id, e.g. `"AIR-HOCKEY"` |
| `name` | `string` | Display name |
| `iconUrl` | `string` (optional) | |

### `LucraMatchupParticipantGroup`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | Group (team) id; the `teamId` for a versus accept |
| `userIds` | `string[]` | User ids of the group's participants; empty when nobody has joined it |

## Matchup details

`api.matchupDetails(matchupId)` resolves with the matchup plus who is in each group, each group's standing and score, and per-player scores.

```typescript
const { matchup, groups, participantScores } = await client.api.matchupDetails(matchupId);
const winner = groups.find((g) => g.id === matchup.winningGroupId);
```

### `LucraMatchupDetails`

| Field | Type | Notes |
| --- | --- | --- |
| `matchup` | `LucraMatchup` | The same object `api.matchup` returns |
| `groups` | `LucraMatchupGroup[]` | Every group, including empty ones, in the same order as `matchup.participantGroups` |
| `participantScores` | `LucraMatchupParticipantScore[]` | Per-player scores ordered by `place`; may be empty |

### `LucraMatchupGroup`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `string` | Group (team) id, matching `matchup.participantGroups[].id` |
| `outcome` | `"WIN" \| "LOSS" \| "TIE"` (optional) | The group's current standing: `WIN` is currently winning or has won, `LOSS` is currently losing. It is not only the final result; use `matchup.winningGroupId` for the final winner |
| `score` | `number` (optional) | The group score with any override applied |
| `participants` | `LucraMatchupParticipant[]` | Empty when nobody has joined the group |

### `LucraMatchupParticipant`

| Field | Type | Notes |
| --- | --- | --- |
| `userId` | `string` | |
| `username` | `string` | |
| `avatarUrl` | `string` (optional) | |
| `individualPayout` | `number` (optional) | What this user receives if their group wins, after the fee and team split. Absent for tenant rewards, and for cash matchups when Lucra has no value yet |

### `LucraMatchupParticipantScore`

| Field | Type | Notes |
| --- | --- | --- |
| `userId` | `string` (optional) | |
| `username` | `string` (optional) | |
| `avatarUrl` | `string` (optional) | |
| `place` | `number` (optional) | Rank, 1 is first |
| `score` | `number` (optional) | |
| `finishedAt` | `string` (optional) | ISO timestamp |
| `groupId` | `string` (optional) | The participant's group |

## Live details

`api.subscribeToMatchupDetails(matchupId)` resolves with the current `LucraMatchupDetails`, then delivers each change to the matchup (a player joins, a score or status changes) as a `matchupDetailsUpdated` event carrying the full, fresh details. The first update may repeat the snapshot. The [end-to-end flow](#end-to-end-flow) shows the listener, subscribe, and cleanup code.

- One subscription at a time: subscribing again replaces it, and only the latest matchup's updates reach listeners.
- `api.cancelMatchupDetailsSubscription()` stops the updates and the Lucra app's live connection. It never throws, so it is safe in cleanup before `open()` or after `close()`.
- `close()` also ends the subscription; subscribe again after reopening.
- After an iframe reload the SDK subscribes again on its own to an active subscription. A subscribe still pending when the iframe reloads is not resent: it rejects with `"Timeout"`, so subscribe again.
- A pending subscribe that a newer subscribe or a cancel replaces rejects with a string starting with `"Cancelled by"`. It is benign: do not show it to users.

## Creating a game

`api.createRecreationalGame(input)` creates a matchup owned by the logged-in user and resolves with a [`LucraRecreationalGameResult`](#result). The Lucra app validates the input, runs the account and buy-in checks, and creates the matchup.

```typescript
await client.ready;
const { matchupId } = await client.api.createRecreationalGame({
  gameTypeId: 'AIR-HOCKEY',
  atStake: { type: 'CASH', amount: 5 },
  playStyle: 'GROUP_VS_GROUP',
});
```

### `LucraCreateRecreationalGameInput`

| Field | Type | Notes |
| --- | --- | --- |
| `gameTypeId` | `string` | Game type id, e.g. `"AIR-HOCKEY"` (`LucraRecreationalGame.gameId`) |
| `atStake` | `LucraCashStake` | `{ type: "CASH", amount: number }`. Cash is the only supported stake |
| `playStyle` | `LucraPlayStyle` | `"GROUP_VS_GROUP"` or `"FREE_FOR_ALL"` |

- A cash `amount` must be a whole number within the tenant's allowed range.
- Tenant-reward stakes are not supported for create: any `atStake.type` other than `"CASH"` rejects with `INVALID_REWARD_TYPE`.
- Invalid input rejects with an `INVALID_*` code whose `message` names the field.

### Result

Creates and accepts resolve with `LucraRecreationalGameResult`: `{ matchupId: string; matchup: LucraMatchup | null }`. After the write the Lucra app reads the matchup back, and `matchup` is `null` only when that read failed. **The write still succeeded**: do not retry; fetch it with `api.matchup(matchupId)`.

Headless writes do not fire the `matchupCreated`, `matchupAccepted`, or `matchupCanceled` events, which come from Lucra's own UI. The resolved promise is the signal.

## Accepting a versus game

`api.acceptVersusRecreationalGame(matchupId, teamId)` joins the logged-in user to one team of a `GROUP_VS_GROUP` matchup and resolves with a [`LucraRecreationalGameResult`](#result). `teamId` is a group id: `matchup.participantGroups[].id`, or `details.groups[].id` (empty groups included). Read the matchup first and let the user pick a team.

```typescript
await client.ready;
const result = await client.api.acceptVersusRecreationalGame(matchupId, teamId);
```

The accept rejects with `NOT_ALLOWED`, and nothing happens, when the matchup is not `OPEN`, the user is already in it, `teamId` is not one of its groups, or the matchup is `FREE_FOR_ALL`. Check `matchup.playStyle` and call the function that matches.

## Accepting a free-for-all game

`api.acceptFreeForAllRecreationalGame(matchupId)` joins the logged-in user to a `FREE_FOR_ALL` matchup. There is no team to pick. Everything else matches the versus accept, including the result and the `NOT_ALLOWED` cases; calling it on a `GROUP_VS_GROUP` matchup rejects with `NOT_ALLOWED`. The two accepts share one in-flight slot: while either is pending, the other rejects at once.

```typescript
await client.ready;
const result = await client.api.acceptFreeForAllRecreationalGame(matchupId);
```

## Canceling a game

`api.cancelRecreationalGame(matchupId)` cancels a matchup and resolves with `{ matchupId }` (`LucraCancelRecreationalGameResult`). Only the creator can cancel, and only while `status` is `OPEN`; anything else rejects with `NOT_ALLOWED`. An unknown id rejects with `API_ERROR` (`"Recreational game matchup not found"`). Canceling refunds the stakes. There are no buy-in checks. The result carries no matchup: read it with `api.matchup(matchupId)` to see the new status.

```typescript
await client.ready;
await client.api.cancelRecreationalGame(matchupId);
```

## Errors and remediation

Every `LucraApiError` code below is documented in full, with completion events, in [Headless on Web: Errors](2.0_headless.md#lucraapierror-by-code).

### Codes by function

| Function | `LucraApiError` codes |
| --- | --- |
| `matchup`, `matchupDetails`, `subscribeToMatchupDetails` | `API_ERROR` |
| `createRecreationalGame` | `NOT_ALLOWED`, `INVALID_AT_STAKE`, `INVALID_REWARD_TYPE`, `INVALID_PLAY_STYLE`, `INSUFFICIENT_FUNDS`, `UNVERIFIED`, `DEMOGRAPHIC_INFORMATION_MISSING`, `LOCATION_NEEDED`, `LOCATION_ERROR`, `API_ERROR` |
| `acceptVersusRecreationalGame`, `acceptFreeForAllRecreationalGame` | `NOT_ALLOWED`, `INSUFFICIENT_FUNDS`, `UNVERIFIED`, `DEMOGRAPHIC_INFORMATION_MISSING`, `LOCATION_NEEDED`, `LOCATION_ERROR`, `API_ERROR` |
| `cancelRecreationalGame` | `NOT_ALLOWED`, `API_ERROR` |

Besides these, any of these functions can reject with `LucraClientNotOpen` or the string `"Timeout"`; the reads also reject with the initialization failure body (`{ success: false }`) when the iframe fails to initialize, and a pending subscribe with a `"Cancelled by"` string.

The writes check in a fixed order:

- **Create:** account (blocked or suspended), input validation, then the buy-in checks.
- **Accept:** account, the matchup checks, then the buy-in checks.
- **Cancel:** account, creator, then status.

The buy-in checks run funds, then identity or demographics, then location. Cash stakes need identity verification (`UNVERIFIED`), or demographics when the tenant defers verification until withdrawal. Reward stakes need demographics and never fail on funds.

| `code` | Cause | Remediation |
| --- | --- | --- |
| `NOT_ALLOWED` | Blocked or suspended account; a matchup not `OPEN`; a user already in it; the wrong accept function; an unknown `teamId`; a cancel by someone other than the creator; or another write of the same kind still pending. `message` says which | Show `message`; do not offer the action again. Exception: `"Another <name> request is already in progress"` is transient: retry after the pending call settles. If your app had no call pending, it came from the Lucra app, where an earlier write is still running with an unknown outcome: read the matchup first |
| `INVALID_AT_STAKE`, `INVALID_REWARD_TYPE`, `INVALID_PLAY_STYLE` | Create input failed validation; `message` names the field | Fix the input |
| `INSUFFICIENT_FUNDS` | The balance does not cover the cash stake | From a click, `client.popup().deposit()`; retry after a successful deposit |
| `UNVERIFIED` | Identity verification is incomplete | `client.dialog().kyc()`; retry on `kycComplete` |
| `DEMOGRAPHIC_INFORMATION_MISSING` | Profile information is missing | `client.dialog().demographic()`; retry on `demographicComplete` |
| `LOCATION_NEEDED` | No location for the user yet | `client.dialog().locationGrant()`; retry on `locationGranted` |
| `LOCATION_ERROR` | The location check failed | Show `message` as is; retry only after a browser-side failure is fixed |
| `API_ERROR` | Reads: `"Recreational game matchup not found"`, or a failed read. Writes: see below | Reads: show `message`; a failed read is safe to retry, a not-found id is not |

[Tournaments Headless: Joining a tournament](2.1_tournaments_headless.md#joining-a-tournament) shows the present-flow-then-retry loop; it works the same for GYP writes.

### Write outcomes: definite or unknown

A rejected write either definitely did nothing, or may have completed.

**Definite: nothing was created, joined, or canceled.** Fix the cause, then call again.

- Any code other than `API_ERROR`.
- `API_ERROR` with `"Recreational game matchup not found"`, `"gameTypeId is required"`, or a message starting `"Request expired before it could be processed"` (the Lucra app received the write too late to run it safely).
- `LucraClientNotOpen` because the client was not open at call time (the message starts `"Cannot call api."`): nothing was sent.

**Unknown: the write may have completed.**

- `"Timeout"`.
- Any other `API_ERROR`, including `"The join was not confirmed; ..."` and `"The cancel was not confirmed; ..."`.
- `LucraClientNotOpen` because `close()` ran while the write was pending (the message starts `"LucraClient was closed while the request was pending"`).

**Never retry a write automatically after an unknown outcome.** A second create makes a second matchup, with a second buy-in for cash. Check first:

| Write | Before calling again |
| --- | --- |
| Create | No headless call lists the user's matchups, so ask the user before creating again |
| Accept | `api.matchup(matchupId)`: accept again only if no `participantGroups[].userIds` contains `client.user.id`. `client.user` comes from the `userInfo` event and can be `null` briefly after `ready`, so wait for it before checking |
| Cancel | `api.matchup(matchupId)`: cancel again only if `status` is still `OPEN` |

A retry that reaches the Lucra app while the earlier write is still running there rejects with `NOT_ALLOWED` (`"Another <name> request is already in progress"`). The earlier write's outcome is still unknown.

## End-to-end flow

The creator creates a matchup and shares its id through your own link (a headless create produces no Lucra invite URL). The second user opens that link, sees the matchup before logging in, and accepts. Both watch it live, the creator can cancel while it is `OPEN`, and play hands off to Lucra UI.

```typescript
import { LucraClient, type LucraMatchupDetails } from 'lucra-web-sdk';

// Your own helpers.
declare function share(url: string): void;
declare function showError(e: unknown): void;

const client = LucraClient.getInstance();

// 1. Creator: create, then share the id through your own route.
async function createAndShare() {
  await client.ready;
  const { matchupId } = await client.api.createRecreationalGame({
    gameTypeId: 'AIR-HOCKEY',
    atStake: { type: 'CASH', amount: 5 },
    playStyle: 'GROUP_VS_GROUP',
  });
  share(`https://your-app.example/games/${matchupId}`);
  return matchupId;
}

// 2. Both users, on your /games/:matchupId page: watch the matchup. Works before login.
// Returns the cleanup to run when the page unmounts.
function watchMatchup(matchupId: string, render: (details: LucraMatchupDetails) => void) {
  client.on('matchupDetailsUpdated', render);
  client.api
    .subscribeToMatchupDetails(matchupId)
    .then(render)
    .catch((e) => {
      if (typeof e === 'string' && e.startsWith('Cancelled by')) return; // replaced or cleaned up
      showError(e);
    });
  return () => {
    client.off('matchupDetailsUpdated', render);
    client.api.cancelMatchupDetailsSubscription();
  };
}

// 3. Second user: join from your button. For versus, teamId is the group the user
// picked from details.groups. The subscription then delivers the change to both users.
async function join({ matchup }: LucraMatchupDetails, teamId?: string) {
  await client.ready; // LucraUserNotLoggedIn: present login, then retry
  if (matchup.playStyle === 'FREE_FOR_ALL') {
    return client.api.acceptFreeForAllRecreationalGame(matchup.id);
  }
  if (!teamId) throw new Error('Pick a team first');
  return client.api.acceptVersusRecreationalGame(matchup.id, teamId);
}

// 4. Creator: show a Cancel button only while it can succeed.
// client.user comes from the userInfo event and can be null briefly after ready.
function canCancel({ matchup }: LucraMatchupDetails) {
  const userId = client.user?.id;
  return userId !== undefined && matchup.status === 'OPEN' && matchup.creatorId === userId;
}

async function cancel(matchupId: string) {
  await client.ready;
  return client.api.cancelRecreationalGame(matchupId);
}

// 5. Play: hand off to Lucra's matchup screen.
function play(matchupId: string) {
  client.dialog().matchupDetails(matchupId);
}
```

Disable each button while its call is pending, and handle rejections per [Errors and remediation](#errors-and-remediation).
