# Headless on Web

Lucra's headless surface lets your app fetch Lucra data and trigger Lucra actions over a Promise-based API, so you can render tournaments, leaderboards, and achievements in your own UI instead of presenting Lucra's screens.

## Headless on Web is an invisible iframe

On Android and iOS, headless calls run in-process against native modules. On Web, headless calls are served by the Lucra app running in an iframe: `client.open(element, phoneNumber, { hidden: true })` mounts an *invisible* iframe that exists solely to run the Lucra app and post results back to the host page. There is no iframe-free mode: every `api.*` call is a `postMessage` to the Lucra app running inside that frame, and every response is a `postMessage` back.

```typescript
import { LucraClient } from 'lucra-web-sdk';

LucraClient.initialize({ apiKey, tenantId, env: 'sandbox' });
const client = LucraClient.getInstance();

// Mount the Lucra app invisibly; it boots, initializes, and answers api.* calls.
client.open(container, undefined, { hidden: true }).home();

const { tournaments } = await client.api.tournaments();
```

Mount it once at app startup, right after `initialize`, so the Lucra app is booting before your first `api.*` call. See [Mount the iframe at startup](1.2_initialize_client.md#mount-the-iframe-at-startup-recommended).

What the iframe model means for your integration:

- **The iframe must be mounted and initialized before anything works.** A request posted before the Lucra app is listening is silently dropped and surfaces as the [15-second timeout](#request-timeout). With no iframe at all (before `open()` or after `close()`), `api.*` calls reject with [`LucraClientNotOpen`](#lucraclientnotopen) and the non-reply `sendMessage.*` calls throw it. Sequence calls behind the [lifecycle gates](#lifecycle-and-gating) below.
- **Headless and UI flows share one iframe.** Calling `show()` (or opening a [dialog](1.3_lucraflows.md#dialogs)) presents the same running app; `redirect()` navigates it. Reloading it drops any in-flight `api.*` request, and both `open(...).login()` (src reload) and the deprecated `moveTo()` (re-parenting reloads the iframe, see [Lucra Flows](1.3_lucraflows.md#visibility-and-placement)) reload it. To present Lucra UI without a reload, use a [dialog](1.3_lucraflows.md#dialogs).
- **One exception: deposits use a real popup window** (`client.popup().deposit()`), because Apple Pay does not run inside a cross-origin iframe. See [Popups](1.3_lucraflows.md#popups).

## When to use headless vs. Lucra flows

Use **headless** when you are rendering Lucra data in your own components — a tournaments list on your home screen, a custom leaderboard, an achievements page — or driving a join from your own button.

Use a **[Lucra flow](1.3_lucraflows.md)** when the step needs Lucra's UI: login, identity verification (KYC), demographic collection, deposits/withdrawals, location grant, matchup creation, and gameplay itself. These flows carry Lucra's compliance and payment obligations; they cannot be rebuilt headlessly.

The two compose: headless calls reject with typed errors that tell you *which* Lucra flow to present, and after the flow completes you retry the call. That loop — **call → typed error → present the matching flow → retry** — is the core of headless integration on Web. See [Errors](#errors).

## Lifecycle and gating

| Member | Type | Meaning |
| --- | --- | --- |
| `LucraClient.initialize(config)` | `(config: LucraClientConstructor) => LucraClient` | Creates the singleton. Throws if already initialized. See [Initializing the LucraClient](1.2_initialize_client.md). |
| `LucraClient.getInstance()` | `() => LucraClient` | Returns the singleton. Throws if `initialize` has not been called. |
| `LucraClient.destroy()` | `() => void` | Removes listeners, closes the iframe, clears the singleton. |
| `client.close()` | `() => void` | Removes the iframe but keeps the singleton, so `open()` mounts Lucra again. In-flight `api.*` requests and a pending `ready` reject at once with [`LucraClientNotOpen`](#lucraclientnotopen): their responses can no longer arrive. A write that was already running may still complete in the Lucra app. Initialization state resets, so the gates below apply anew after reopening. |
| `initialized` event | `{ success: boolean }` | Fired when the Lucra iframe finishes booting. See [Lucra Event Listener](1.6_lucra_event_listener.md). |
| `client.isInitialized` | `boolean` | `true` once the iframe reported successful initialization. |
| `client.ready` | `Promise<void>` | Resolves once the iframe is initialized **and** the user is logged in. Rejects with the initialization failure body if init fails, or with [`LucraUserNotLoggedIn`](#lucrausernotloggedin) if the user is not logged in. A pending `ready` rejects with [`LucraClientNotOpen`](#lucraclientnotopen) when `close()` runs. Rebuilt automatically after `loginSuccess`, so it can be re-awaited. |
| `client.user` | `SDKLucraUser \| null` | The current Lucra user, populated from `userInfo` events. `null` before login. |

Gate auth-required calls on `ready`:

```typescript
try {
  await client.ready;
  const { achievements } = await client.api.achievements();
} catch (err) {
  if (err instanceof LucraUserNotLoggedIn) {
    client.open(container).login(); // present login, retry after loginSuccess
  }
}
```

A `ready` rejection does **not** mean you must force the login flow immediately: pre-auth reads (`api.tournaments()`, `api.matchup()`, `api.matchupDetails()`, `api.gamesMatchupFee()`) are legitimate, and navigating to login reloads the shared iframe and drops any in-flight request. Open the destination you actually want; the Lucra app gates it and shows login itself when needed.

## API functions

Every function returns a Promise resolved by the Lucra app's response message. Each request carries its own id, so the reads (`achievements`, `tournaments`, `tournament`, `tournamentLeaderboard`, `matchup`, `matchupDetails`, `gamesMatchupFee`) run concurrently: a new call never affects one already in flight, and each settles with its own response. The writes `joinTournament` and `autoJoinTournaments` are **single-flight**: a new call cancels the in-flight one, which rejects with the string `"Cancelled by new <name> request"`. Treat that specific rejection as benign (see [Cancellation](#cancellation)). `createRecreationalGame`, the two accepts (`acceptVersusRecreationalGame`, `acceptFreeForAllRecreationalGame`), and `cancelRecreationalGame` are not single-flight: while one is pending, a new call of the same kind rejects at once with `NOT_ALLOWED`. The two accepts share one slot, so either one rejects while the other is pending. Every request has its own [timeout](#request-timeout): 15 seconds, except `createRecreationalGame`, the two accepts, and `cancelRecreationalGame`, which have 60.

Every call rejects with [`LucraClientNotOpen`](#lucraclientnotopen) before `open()` or after `close()`.

| Function | Signature | Returns | Auth | Init handling |
| --- | --- | --- | --- | --- |
| `api.achievements()` | `() => Promise<LucraAchievementsResponse>` | `{ achievements: LucraAchievement[] }` | Logged-in user required | Sends immediately — call after `ready` |
| `api.tournaments()` | `() => Promise<LucraTournamentsResponse>` | `{ tournaments: LucraTournament[] }` | **None** (pre-auth allowed) | Awaits `initialized` internally |
| `api.tournament(matchupId)` | `(matchupId: string) => Promise<LucraTournamentResponse>` | `{ tournament: LucraTournamentDetail \| null }` | Logged-in user required | Sends immediately — call after `ready` |
| `api.tournamentLeaderboard(matchupId, pagination?)` | `(matchupId: string, pagination?: { limit?: number; offset?: number }) => Promise<LucraTournamentLeaderboardResponse>` | `{ ui_tournament_details: LucraTournamentDetail \| null }` | Logged-in user required | Sends immediately — call after `ready` |
| `api.joinTournament(tournamentId)` | `(tournamentId: string) => Promise<LucraJoinTournamentResponse>` | `{ matchupId: string }` | Logged-in user required | Sends immediately — call after `ready` |
| `api.autoJoinTournaments()` | `() => Promise<LucraAutoJoinedTournamentsBody>` | `{ matchupIds: string[] }` | Logged-in user required | Sends immediately — call after `ready` |
| `api.matchup(matchupId)` | `(matchupId: string) => Promise<LucraMatchup>` | `LucraMatchup`, see [Games You Play Headless](2.2_gyp_headless.md#reading-a-matchup) | **None** (pre-auth allowed) | Awaits `initialized` internally |
| `api.matchupDetails(matchupId)` | `(matchupId: string) => Promise<LucraMatchupDetails>` | `LucraMatchupDetails`, see [Games You Play Headless](2.2_gyp_headless.md#matchup-details) | **None** (pre-auth allowed) | Awaits `initialized` internally |
| `api.gamesMatchupFee()` | `() => Promise<number>` | The games (minigame) matchup service fee as a fraction (`0.05` is 5%), `0` when none is configured, see [Games You Play Headless](2.2_gyp_headless.md#fee) | **None** (pre-auth allowed) | Awaits `initialized` internally |
| `api.subscribeToMatchupDetails(matchupId)` | `(matchupId: string) => Promise<LucraMatchupDetails>` | The current `LucraMatchupDetails`; later changes arrive as `matchupDetailsUpdated` events, see [Games You Play Headless](2.2_gyp_headless.md#live-details) | **None** (pre-auth allowed) | Awaits `initialized` internally |
| `api.cancelMatchupDetailsSubscription()` | `() => void` | Nothing; stops `matchupDetailsUpdated` events, see [Games You Play Headless](2.2_gyp_headless.md#live-details) | **None** | Never throws; safe before `open()` and after `close()` |
| `api.createRecreationalGame(input)` | `(input: LucraCreateRecreationalGameInput) => Promise<LucraRecreationalGameResult>` | `{ matchupId: string; matchup: LucraMatchup \| null }`, see [Games You Play Headless](2.2_gyp_headless.md#creating-a-game) | Logged-in user required | Sends immediately: call after `ready`. 60-second timeout |
| `api.acceptVersusRecreationalGame(matchupId, teamId)` | `(matchupId: string, teamId: string) => Promise<LucraRecreationalGameResult>` | `{ matchupId: string; matchup: LucraMatchup \| null }`, see [Games You Play Headless](2.2_gyp_headless.md#accepting-a-versus-game) | Logged-in user required | Sends immediately: call after `ready`. 60-second timeout |
| `api.acceptFreeForAllRecreationalGame(matchupId)` | `(matchupId: string) => Promise<LucraRecreationalGameResult>` | `{ matchupId: string; matchup: LucraMatchup \| null }`, see [Games You Play Headless](2.2_gyp_headless.md#accepting-a-free-for-all-game) | Logged-in user required | Sends immediately: call after `ready`. 60-second timeout |
| `api.cancelRecreationalGame(matchupId)` | `(matchupId: string) => Promise<LucraCancelRecreationalGameResult>` | `{ matchupId: string }`, see [Games You Play Headless](2.2_gyp_headless.md#canceling-a-game) | Logged-in user required | Sends immediately: call after `ready`. 60-second timeout |

"Auth required" is enforced by the Lucra app, not the SDK: a gated call issued while logged out is never answered and rejects with the timeout, not a typed error. Sequencing after `ready` is what makes gated calls reliable.

### Achievements

`api.achievements()` resolves with the current user's achievement progress for rendering a custom achievements screen.

```typescript
await client.ready;
const { achievements } = await client.api.achievements();
const completed = achievements.filter((a) => a.isEarned);
```

Each `LucraAchievement` carries `id`, `isEarned`, `earnedAt`, `claimedAt`, three progress fields, and a nested `achievement` definition (`title`, `description`, `iconUrl`, `gameId`, `criteriaType`, optional `catalogReward`).

| Field | Type | Meaning |
| --- | --- | --- |
| `currentValue` | `number` | Raw stored progress toward the goal, e.g. the best score so far or the number of wins. |
| `targetValue` | `number` | The goal the criteria requires, e.g. the score threshold or the win count. `0` when the criteria config is malformed. |
| `currentProgress` | `number` | Floored completion percentage (0-100). Always `100` once earned. |

Render `currentValue / targetValue` as text and use `currentProgress` for progress bar fill only — deriving a point total from the percentage loses precision.

```typescript
const label = `${a.currentValue} / ${a.targetValue}`; // "261 / 700"
const barWidth = `${a.currentProgress}%`; // "37%"
```

## sendMessage functions

Messages your app pushes *into* the Lucra app. These are fire-and-forget (no Promise, no timeout) — but like every postMessage, they are dropped if sent before the iframe is initialized. Before `open()` or after `close()`, all except the replies (`deepLinkResponse`, `convertToCreditResponse`) throw [`LucraClientNotOpen`](#lucraclientnotopen); the replies are dropped.

| Function | Payload | Purpose |
| --- | --- | --- |
| `sendMessage.userUpdated(data)` | `SDKClientUser` — `{ username?, avatarURL?, phoneNumber?, email?, firstName?, lastName?, address?: { address?, addressCont?, city?, state?: StateCode, zip? }, metadata?: Record<string, string> \| null }` | Prefill known user info to shorten Lucra's forms (KYC, demographics). `metadata.externalId` links your user to the Lucra user. Throws synchronously if `metadata` has non-string keys/values. See [Updating Users](1.8_updating_users.md). |
| `sendMessage.navigate(data)` | `{ pathname: string }` | Navigate the Lucra iframe to a pathname within the Lucra app (e.g. `'/app/home'`). Prefer the typed [`redirect()`](1.3_lucraflows.md#redirect-lucra) builder where one exists. |
| `sendMessage.availableRewards(data)` | `{ rewards: LucraReward[] }` — each `{ rewardId, title, descriptor, iconUrl, bannerIconUrl, disclaimer, metadata }` | Supply reward options for free-to-play contests. See [Rewards](1.9_rewards.md). |
| `sendMessage.enableConvertToCredit()` | none | Enable the convert-to-credit option on the withdraw screen. See [Convert to Credit](1.7_convert_to_credit.md). |
| `sendMessage.convertToCreditResponse(data)` | `LucraConvertToCreditResponse` — `{ id, title, iconUrl?, conversionTerms, convertedAmount, convertedDisplayAmount, shortDescription, longDescription, metaData? }` | Answer a `convertToCredit` event with your credit offer. See [Convert to Credit](1.7_convert_to_credit.md). |
| `sendMessage.deepLinkResponse(data)` | `{ url: string }` | Answer a `deepLink` event with the transformed URL. For matchup invites prefer `setMatchupDeepLinkHandler`. See [Deeplinks](1.4_deeplinks.md). |

## Errors

Headless failures surface five ways: a typed `LucraUserNotLoggedIn` error, a typed `LucraClientNotOpen` error, a typed `LucraApiError` with a `code`, the initialization failure body (`{ success: false }`, rejected by `client.ready` and `api.tournaments()` when the iframe fails to initialize), or a **plain string** rejection (timeout / cancellation). Use `instanceof` to distinguish the typed errors and check for the initialization failure body separately; anything else is a string.

Every error below states its remediation and whether retrying is appropriate. The remediation flows are Lucra UI — present them, listen for the matching completion event, then retry the original call.

### `LucraUserNotLoggedIn`

Thrown by `ready` (and cached on it until `loginSuccess` rebuilds the promise) when the session has no logged-in user.

| | |
| --- | --- |
| Surfaces from | `await client.ready` |
| Remediation | Present login: `client.open(element).login()` |
| Retry | Yes — after the `loginSuccess` event fires, re-await `client.ready` and reissue the call |

### `LucraClientNotOpen`

Thrown when a method that needs the Lucra iframe runs before `open()` or after `close()`. `api.*` calls reject with it instead of timing out or hanging. `close()` also rejects every pending `api.*` request, and a pending `ready`, with it; its message says the client was closed while the request was pending.

| | |
| --- | --- |
| Surfaces from | Every `api.*` call (rejection), `await client.ready` (when `close()` runs while pending); `sendMessage.userUpdated()`, `sendMessage.navigate()`, `sendMessage.enableConvertToCredit()`, `sendMessage.availableRewards()`, the methods returned by `redirect()` and `dialog()`, `logout()`, `hide()`, `show()`, `moveTo()` (thrown) |
| Remediation | Mount the iframe first: `client.open(element)` (`{ hidden: true }` for pure headless) |
| Retry | Reads: yes, after `open()`. Writes (`joinTournament`, `createRecreationalGame`, `acceptVersusRecreationalGame`, `acceptFreeForAllRecreationalGame`, `cancelRecreationalGame`): a write rejected because `close()` ran while it was pending has an **unknown outcome**, so check before retrying (for a create, the user's matchups; for an accept, the matchup's groups or participants; for a cancel, the matchup's status). A write rejected because the client was not open yet was never sent and is safe to retry after `open()` |

### `LucraApiError` by `code`

`LucraApiError` extends `Error` (so `message` is populated) and carries `code: LucraApiErrorCode`. `api.joinTournament()` and `api.autoJoinTournaments()` reject with the codes below; the reads (`achievements`, `tournaments`, `tournament`, `tournamentLeaderboard`) reject with `API_ERROR` when the Lucra app fails to fetch the data. `autoJoinTournaments` surfaces the subset `LOCATION_NEEDED`, `DEMOGRAPHIC_INFORMATION_MISSING`, `LOCATION_ERROR`, and `API_ERROR` — `UNVERIFIED` and `INSUFFICIENT_FUNDS` do not apply because the auto-joined tournaments are free. The codes are not call-specific — other `api.*` functions may surface them in the future.

| `code` | Meaning | Remediation | Retry? |
| --- | --- | --- | --- |
| `UNVERIFIED` | The user has not completed identity verification | Present KYC: `client.dialog().kyc()`, close on the `kycComplete` event | Yes — retry after KYC completes |
| `DEMOGRAPHIC_INFORMATION_MISSING` | Required profile/demographic info is missing | Present the form: `client.dialog().demographic()`, close on `demographicComplete` | Yes — retry after the form completes |
| `INSUFFICIENT_FUNDS` | The user's balance does not cover the buy-in | Present deposit **in a popup**: `client.popup().deposit()` — a popup, not an iframe, because Apple Pay does not run cross-origin; observe the result via `popup.onClose(result)` | Yes — retry after a successful deposit |
| `LOCATION_NEEDED` | Lucra has no location for the user yet (the iframe was never granted browser geolocation) | Present the grant page: `client.dialog().locationGrant()` — browsers only grant an iframe location from a user gesture inside it; close on the `locationGranted` event | Yes — retry after `locationGranted` |
| `LOCATION_ERROR` | The location check ran and failed. Two causes share this code: Lucra's geolocation service rejected the location (outside a permitted region), or the browser's own geolocation request failed (permission denied, position unavailable, timeout). `message` says which | Show `error.message` to the user as-is. It is a curated message that carries the geocompliance information the user needs; do not replace it with your own generic text. If it describes a browser geolocation failure, the user can fix it (allow location in the browser) | Only after a browser-side failure is fixed. **No** for a rejected region — the answer will not change this session |
| `NOT_ALLOWED` | The user or the matchup's state does not permit the action: a blocked or suspended account, a matchup that is no longer open, a user who already joined it, or a cancel by someone other than the creator, or of a matchup that is not `OPEN`. The SDK itself raises it, with nothing posted, for a second `createRecreationalGame` while one is pending. It does the same for a second accept (`acceptVersusRecreationalGame` or `acceptFreeForAllRecreationalGame`) while either accept is pending, and for a second `cancelRecreationalGame` while one is pending. `message` says which | Show `error.message`; do not offer the action again | **No**, the answer will not change on retry |
| `INVALID_AT_STAKE` | The create input's stake is invalid: missing, a cash amount outside the tenant's allowed range, or a reward without a `rewardId`. Checked before any network call | Show `error.message` (it names the invalid field) and fix the input | **No**, not with the same input |
| `INVALID_REWARD_TYPE` | The create input's stake type is neither `CASH` nor `TENANT_REWARD`. Checked before any network call | Show `error.message` and fix the input | **No**, not with the same input |
| `INVALID_PLAY_STYLE` | The create input's play style is not a supported value. Checked before any network call | Show `error.message` and fix the input | **No**, not with the same input |
| `API_ERROR` | Catch-all: an API or network failure with no more specific code | Surface `error.message` (it carries the API's detail) | Yes — safe to retry; transient failures are the common cause. Exception: `autoJoinTournaments` uses this code with a message beginning `Auto-join skipped:` for preconditions such as the feature not being enabled for the tenant — those do not change on retry |

The join checks run in a fixed order: funds, then identity or demographics, then location. Paid tournaments require identity verification (`UNVERIFIED`); free-buy-in tournaments — and tenants configured to defer identity verification until withdrawal — require demographic information instead (`DEMOGRAPHIC_INFORMATION_MISSING`). A tournament never rejects with both. Free tournaments never reject with `INSUFFICIENT_FUNDS`.

```typescript
import { LucraApiError, LucraApiErrorCode } from 'lucra-web-sdk';

try {
  const { matchupId } = await client.api.joinTournament(tournamentId);
} catch (e) {
  if (e instanceof LucraApiError) {
    switch (e.code) {
      case LucraApiErrorCode.unverified: {
        const dialog = client.dialog().kyc();
        client.on('kycComplete', () => dialog.close()); // then retry the join
        break;
      }
      case LucraApiErrorCode.insufficientFunds: {
        const popup = client.popup().deposit();
        popup.onClose((result) => {
          if (result?.toastType === 'success') { /* retry the join */ }
        });
        break;
      }
      // ...see the table above for every code
    }
  }
}
```

For a complete join example, including the `locationGranted` listen-close-retry pattern and listener cleanup, see [Tournaments Headless → Joining a tournament](2.1_tournaments_headless.md#joining-a-tournament).

### Request timeout

Each `api.*` request rejects with the string `"Timeout"` if no response arrives within **15 seconds** of that call (**60 seconds** for `createRecreationalGame`, the two accepts, and `cancelRecreationalGame`). Concurrent calls time out independently. A timeout usually means the request was never received or never answered, not that Lucra is slow. Causes, most common first:

| Cause | Fix |
| --- | --- |
| Request sent before the iframe finished initializing (the postMessage was dropped) | Sequence behind `initialized` / `ready`. (`api.tournaments()` is exempt — it awaits init internally.) |
| Auth-gated call issued while logged out — the Lucra app never answers | Gate on `client.ready`; handle `LucraUserNotLoggedIn` |
| The account is blocked or suspended — Lucra gates these before the join route renders, so a `joinTournament` request is never answered | Nothing to retry; the user's account state has to change |
| The iframe was reloaded mid-request (`open(...).login()` forced a src reload, or the deprecated `moveTo()` re-parented the iframe) | Don't navigate, reload, or re-parent the iframe while a request is in flight |
| A genuinely slow backend call inside the Lucra app (a failed one rejects with [`LucraApiError`](#lucraapierror-by-code) instead) | Retry; if persistent, check status with Lucra support |

### Cancellation

Only the writes and the live details subscription cancel. A new call to `api.joinTournament()` or `api.autoJoinTournaments()` cancels the in-flight one, which rejects with the string `"Cancelled by new <name> request"` (e.g. `"Cancelled by new joinTournament request"`). Treat it as benign, never as a failure to surface to users. `api.createRecreationalGame()`, `api.acceptVersusRecreationalGame()`, `api.acceptFreeForAllRecreationalGame()` and `api.cancelRecreationalGame()` never cancel: a second call of the same kind while one is pending (for the two accepts, either one while the other is pending) is rejected instead, and the first keeps going. Reads (including `matchup`, `matchupDetails` and `gamesMatchupFee`) run concurrently and never cancel each other: calling one twice settles both promises, each with its own response. A new `api.subscribeToMatchupDetails()` call or `api.cancelMatchupDetailsSubscription()` rejects a pending subscribe with a string starting with `"Cancelled by"`, equally benign (see [Live details](2.2_gyp_headless.md#live-details)). The SDK has no framework dependency, but frameworks that double-invoke effects in development (for example React StrictMode) trigger write cancellation; the [`lucra-web-headless`](skills/lucra-web-headless/SKILL.md#framework-notes) skill lists the known framework interactions.
